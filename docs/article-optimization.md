## 已实施的改动

| 文章思路 | 项目原有开销 | 本次行为 |
| --- | --- | --- |
| 独立更新选择 / 高亮 | 每次选择都克隆场景树、重新生成 `flat`，Worker 回传完整数据，React 随后触发整场景 WASM 同步 | Worker 缓存当前版本的树与几何；选择只返回项目、版本、选中 ID，主线程保留树与几何的引用，仅调用选择接口 |
| 合并高频事件 | 每个 `pointermove` 都调用 WASM 或执行软渲染拖动计算 | 渲染帧前处理最新位置；开始拖动跨过 4px 阈值时立即处理一次，避免移出又移回被误判为点击；松手提交最终位置 |
| 增量上传缓冲 | 拖动一个对象时重传全部实例及全部包围球 | 按实例下标只写该对象的实例记录与包围球；松手后的场景提交与撤销流程保持完整 |
| 缩小重复扫描范围 | 每个可见实例都在线性模型列表中查找三角面数量，HUD、统计和绘制又各自计算可见性 | 每帧各扫描一次包围球和模型，复用可见掩码、可见数、三角面数和视锥平面 |

主要实现：

- `frontend/src/workers/sceneModel.ts`：缓存几何快照，编辑、撤销、重做和打开项目时失效。
- `frontend/src/workers/scene.worker.ts`、`bridge.ts`：新增 `selectionChanged` 消息，校验项目和版本后合并。
- `frontend/src/engine/frameInput.ts`、`components/Viewport.tsx`：合并移动事件，并处理按下、滚轮、松手、取消和释放资源的边界。
- `engine-rs/data-wind-engine/src/lib.rs`、`engine-rs/oxgpu/src/culler.rs`：按偏移更新单个实例和包围球。
- `engine-rs/data-wind-engine/src/visibility.rs`、`render.rs`：共享每帧可见性计算，保留并复用掩码内存。

### 开销变化

拖动预览一次更新的两类场景缓冲上传量由 `N × (48 + 32)` 字节变为固定 `80` 字节。在 1024 个模型的上限场景中，这部分从 81,920 字节降为 80 字节。此数值不包含每帧 uniform、egui 和松手提交后的场景同步。

可见性和模型三角面统计由最坏 `O(N × M)` 改为 `O(N + M)`，其中 N 为实例数、M 为模型实例数。同一帧的模型绘制、egui HUD 和统计事件共享计算结果。

## 可复现的统计微基准

环境：macOS x86_64，Rust 1.95.0，原生优化编译。每组预热 100 次、测量 2000 次，使用全部模型可见的合成场景，并先验证两种算法的统计结果一致。

| 合成场景 | 原算法每次 | 新算法每次 | 本次测量加速比 |
| --- | ---: | ---: | ---: |
| 70 个可见模型 | 1.54 μs | 0.46 μs | 3.3 倍 |
| 1024 个可见模型 | 214.03 μs | 7.48 μs | 28.6 倍 |

这是 CPU 统计步骤的原生微基准，不代表浏览器 WASM 耗时或整体帧率提高相同比例；GPU 渲染、模型复杂度和其他 UI 开销不在测量范围内。

在 `engine-rs` 目录运行：

```bash
cargo run -p native-probe --release --example visibility_bench
```

也可以只编译不依赖 GPU 的基准源码，避免首次构建原生 wgpu：

```bash
rustc --edition=2024 -O probe/examples/visibility_bench.rs -o /tmp/data-wind-visibility-bench
/tmp/data-wind-visibility-bench
```

## 架构取舍与后续边界

当前已有 `SceneNode` 语义树与派生的 `FlatInstance` 渲染数据，以及 50 步有界快照撤销。本次沿用这些职责和存储格式。

2026-11-01 已将引擎的帧事件返回接入 FlatBuffers `CommandResponse`：单一 schema、Rust / TypeScript 生成代码、版本与长度检查，以及跨语言和真实 Wasm ABI 测试均已落实。鼠标输入仍通过 WASM 数值参数传递，结构或属性编辑提交保留 JSON。字段读取无需 JSON 解析，当前独立字节返回值仍包含 JS / WASM 之间的复制；完整取舍与复现命令见 [引擎通信契约](engine-protocol.md)。

固定原点与 f64 世界坐标适合后续真实 GIS / 测绘坐标接入；当前数据是本地场景坐标，实施这一方案需要同时设计相机、拾取、属性编辑、保存和导入坐标的转换闭环。空间索引和大批量拖放包围盒预览也需要随更大场景或批量放置功能设计。

工作区同时进行的模型库扩展和按场景加载资源改动已保留；这些不计入上述交互与统计优化的测量结果。

## 2026-11-01 第二轮：view origin 大坐标平移

文章的 `view_origin` 技巧：f32 只剩约 7 位有效数字，当世界坐标本身很大（UTM 东坐标 16 万–83 万、北坐标可达千万）时，厘米级细节在 GPU 里抖动。做法是加载时取一次场景中心存为原点，之后 GPU 全程使用相对坐标，每帧不做任何平移。

本次落地的取舍：**原点放在前端，引擎零改动**。wasm 引擎继续只认 f32 相对坐标；f64 语义树在前端 Worker，`openProject` / `loadScene` 时计算一次可渲染对象（模型 / 标记点 / 飞线含端点 / 围栏）的 XZ 包围盒中心，前端在同步边界做平移：

- 进引擎：`sync_scene` 的 flat 位置、`camera_view` 目标点、`screen_position` 入参减去原点（`frontend/src/engine/viewOrigin.ts` 的 `toEngineFlat` / `toEnginePoint`）。
- 出引擎：`TransformEvent` 回传位置、`position_on_plane` 返回值、`camera_state` 目标点加回原点（`fromEnginePoint`）。
- 场景树、撤销快照、持久化与导出的坐标全部保持世界坐标，原点只存在于渲染边界。

关键约束：

- **只平移 XZ**。Y 是地面高度：栅栏 y=0、相机仰角限制、网格与地面都建立在"地面在 y=0"之上，平移 Y 会破坏这些结构假设；实践中大坐标出现在 XZ（地理 / 工程偏移），Y 是海拔，量级小。
- **激活阈值 1e5**。坐标绝对值不超过 1e5 的场景返回零原点，行为与历史版本逐位一致；超过才启用平移，避免小场景无谓位移和旧书签漂移。
- **原点在加载时定死**。会话中途编辑不重算，否则每次编辑都会移动世界、让已保存视角跳变。`appendScene` 亦沿用加载时原点；若后续出现"追加远距离子场景"需求，再引入显式的重设原点操作。
- **软件渲染路径不参与**。Canvas2D 回退全程 JS f64，没有 f32 精度问题；其相机与世界坐标保持绝对值。附带收益：引擎相机复位目标 (2,2,0) 在相对空间下等于"看向场景中心"，比旧的绝对 (2,2,0) 对大坐标场景更合理。
- 引擎侧网格 / 地面固定在世界原点，平移后即场景中心附近，大坐标场景下网格终于落在对象脚下。

验证：新增 `frontend/src/tests/viewOrigin.test.ts` 8 项（阈值、飞线端点、非渲染节点忽略、往返换算、flat 不变异），全套 60 项测试通过；`tsc --noEmit` 对本次改动文件无错误（`src/viewer/` 为进行中的未跟踪文件，其类型错误与本次无关，见下）；Oxlint 无新增警告；引擎与协议无改动，无需重建 wasm。

注：`frontend/src/viewer/canvasHost.ts` 是工作区里另一份进行中的代码（未跟踪），当前 `pnpm typecheck` / `pnpm build` 会因它报错；本轮改动不依赖、不触碰该文件。

## 模式储备（文章中尚未落地、待对应功能出现时照做）

- **命令状态机（文章的 `CadCommand`）**：工具激活后按步骤喂输入，每步是纯函数并产出预览事件，完成才提交实体。触发时机：框选区域、画标注、测量距离等多步交互工具接入引擎时，按此模式在 `EngineEvent` 增加 `CommandPrompt` / 预览类事件（协议文档已预留 union 追加规则）。
- **大批量放置的包围盒幽灵**：批量导入 / 粘贴大量对象时先只画一个包围盒幽灵，落点确认后才展开成真实实例，避免一次卡顿。触发时机：批量导入或剪贴板批量粘贴功能出现时；届时可一并评估文章的空间索引（网格桶）是否需要用于对齐 / 吸附。
