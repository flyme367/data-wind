# 用 egui 原生控件实现菜单控件（视觉替换，交互协议不动）

## Context

用户问了两件事：① egui 有哪些控件；② 实现项目菜单里对应的控件。

已确认的事实：
- **egui 0.37 原生控件**（本机 Cargo 源码核实）：widgets 模块有 `Label`、`TextEdit`、`Button`（0.37 已合并 `SelectableLabel`/`ImageButton` → `Button::selectable()`/`Button::image()`）、`Checkbox`、`RadioButton`、`Slider`、`RangeSlider`、`DragValue`、`ProgressBar`、`Spinner`、`Image`、`Separator`、`color_picker` 模块；容器有 `ComboBox`、`CollapsingHeader`、`Window`、`ScrollArea`、`Menu`、`Popup`、`Tooltip`、`Grid` 等。**egui 没有独立"开关 Switch"和"树 Tree"控件**（`ToggleValue` 已移除）。
- **菜单 28 个控件已全部实现**（`controlCatalog.ts` ↔ `WIDGET_KINDS`），但全在 `board/controls.rs` / `board/widgets.rs` 里用 `egui::Painter` 手绘，未用任何原生控件。
- **完整原生交互重构不可行**（已核实）：看板从不喂 `RawInput.events`（`board/mod.rs:491`）；原生弹层（ComboBox/Window）画在其他 egui layer，会被 `frame()` 的按层捕获丢弃；中文 IME 依赖 DOM 隐藏 textarea（`boardCanvas.ts:93`），换原生 TextEdit 会退化；先 tessellate 再 `node.world()` 旋转/缩放的逐顶点管线要求全部形状在 node 局部坐标。

**方向**（推荐项，用户未答复，按此执行）：有原生对应的控件改用 egui 原生控件**绘制**——在 node 自己的 layer 里建 `egui::Ui`（纯画笔，交互不走 egui），深色主题用 `Visuals` 定制贴近现有风格；自研 pointer 协议、弹层路径、IME 流程、TS 侧全部不动。无原生对应的控件保持手绘。

## 技术依据（已核实 API）

- `Ui::new(ctx, scope_id, UiBuilder)` 公开（egui 0.37 `ui.rs:94`）；`UiBuilder` 有 `.layer_id()` `.max_rect()` `.id()` `.style()`
- `Painter::layer_id()` 公开（`painter.rs:156`）——用 `frame()` 层捕获（`board/mod.rs:511`）同款 layer id，原生控件 shapes 才会被捕获进 BoardFrame
- `Checkbox::new(&mut bool, text)`、`Button::new(text).fill().stroke().min_size().corner_radius()`、`Slider::new(&mut f64, min..=max).show_value(false).custom_formatter()`、`ProgressBar::new(f32).fill().show_percentage()`、`ComboBox::from_id_salt(id).selected_text(..).show_ui(&mut ui, |_| {})`（无事件永不弹层，只画收起态按钮+箭头）、`color_picker::show_color_at(painter, color, rect)`（painter 级，无需 Ui）

## 改动

### 1. `engine-rs/data-wind-engine/src/board/mod.rs`
- 新增 `board_style(radius: f32) -> egui::Style`：基于 `Visuals::dark()`，对齐现有手绘色板——`selection.bg_fill`/`hovered.bg_fill` = `ACCENT`、`widgets.inactive.fg_stroke` = `TEXT`、`extreme_bg_color`（滑轨/输入底）= `#0a1522`、`widgets.*.corner_radius` = `radius`、`spacing.button_padding = 0`、`item_spacing = 0`、`icon_spacing ≈ 8`。
- 新增 `BoardScene::paint_ui(...)` 辅助：`Ui::new(self.context.clone(), scope_id, UiBuilder::new().layer_id(p.layer_id()).max_rect(rect).clip_rect(p.clip_rect()).id(Id::new(("ctl", &node.id))))`，供 controls.rs 各分支使用。

### 2. `engine-rs/data-wind-engine/src/board/controls.rs` — `paint_control` 分支替换

| kind | 原生控件 | 说明 |
|---|---|---|
| `dropdown` / `timePicker` | `ComboBox` 收起态 | 只画原生按钮+箭头；弹层仍走 `paint_popup`/`popup_rect`/`pointer()` 自研路径（此处不动） |
| `checkbox` | `Checkbox` | `centered_and_justified` 垂直居中；checked 取自现有 ControlState/`data["checked"]` 逻辑（`controls.rs:430`） |
| `slider` / `timeProgress` | `Slider` | 子 Ui max_rect=滑轨加高区（复用 `slider_track()` 预留 75px 右侧数值位）；min/max/值复用现有读取逻辑（`:465-470`）；`timeProgress` 用 `.custom_formatter(duration)`；右侧数值 label 保持手绘 |
| `progress` | `ProgressBar` | 子 Ui max_rect=现有 track 矩形（`:418-421`），`.fill(ACCENT)`；标题/百分比 label 保持手绘 |
| `list` / `menuVertical` / `menuHorizontal` 行、`tabs` 表头 | `Button::selectable` | 逐项/逐 tab 建 max_rect=单元格的子 Ui，`centered_and_justified` + `Button::selectable(active, item)`；active 判定复用现有逻辑（`:339, :265-267`） |
| `colorPicker` | `show_color_at` | 色块部分（`:497-500`）换原生渐变边色块；文本保持 |

**保持手绘不动**（egui 无原生对应或原生方案会被层捕获/键盘事件卡死）：`switch`（egui 无开关控件）、`input`/`search`（TextEdit 需键盘事件，DOM textarea 方案已覆盖且 IME 更优）、`dialog`（Window 是 Area 层会被丢弃）、`tree`、`groupPanel`、`timeRange`、`upload`、`iframe`、`twin2d`，以及全部图表/地图/媒体/文本类。

### 3. `engine-rs/data-wind-engine/src/board/widgets.rs`
- 把 `"button"` 从 `styled_text` 分支（`widgets.rs:218`）摘出，改在 `paint_control` 新增 `"button"` 分支用原生 `Button` 实现（`fill`=w.background、`corner_radius`=w.radius、`min_size`=body、RichText size=font_size）。交互（`pointer()` 无 button 分支，按钮目前纯展示）不变。

### 4. 不改动
- TS 侧零改动（无新 kind、无协议变化、缩略图 chartSvg 不涉及）。
- `probe/tests/board.rs` 断言不改（每 kind 非空几何/可见像素对原生控件绘制依然成立）。

## 验证

1. **Rust 测试**：`cd engine-rs && ~/.cargo/bin/cargo test -p probe --test board`（cargo 不在 PATH，用全路径；8 组既有行为含逐 kind 几何/旋转命中/控件状态保留必须全绿）。
2. **wasm 重建**：`cd frontend && pnpm build:engine`，随后 `pnpm test`（vitest）+ `pnpm typecheck`。
3. **视觉验证**（沿用 dw-visual-verify-workflow）：headless Chrome + CDP 注入 dw_* localStorage 截真实画面；重点看 checkbox/slider/timeProgress/progress/button/dropdown 收起态/列表行/tab 表头/颜色块是否为原生外观且无错位；必要时 `dw_disable_webgpu=1` 走 CPU 光栅路径确认 `snapshot`/PNG 导出同样正常。
4. **交互回归**：预览模式点击 checkbox/switch（Change 事件）、拖 slider（数值跟随）、开 dropdown 弹层选选项、input 聚焦 DOM textarea 输入——全部走原协议，必须与改前一致。

## 风险与回退

- 原生控件默认外观与暗色看板有差异 → 由 `board_style` 的 Visuals 定制吸收；个别控件若效果不佳，该分支单独回退手绘（分支隔离清晰，不影响其他控件与协议）。
- 原生控件会在 ctx memory 写入动画/WidgetRect 状态——无事件下是静态的，与自研 `controls` 状态机无双源冲突（checkbox/checkbox 值、slider 值都由我们每帧从 ControlState 写入局部变量再传 `&mut`）。
